# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A cached GitLab CLI with time-tracking helpers: a caching daemon (`forskapd`) that talks to GitLab and serves a varlink IPC socket, and a thin CLI (`forskap`, crate `forskap-cli`) that talks only to the daemon. Cargo workspace, Rust edition 2024, requires Rust 1.85+.

## Commands

```sh
cargo build                                   # whole workspace
cargo test                                    # all tests (inline #[cfg(test)] modules, no tests/ dirs)
cargo test -p forskapd <name>                 # single test by name filter
cargo fmt                                     # formatting is enforced; run before committing
cargo run -p forskapd --bin gen-config-template   # annotated default daemon config
cargo bench -p forskapd                       # local perf suite (never in CI; see forskapd/docs/benchmarks.md)
cargo bench -p forskapd -- --save-baseline main   # record baseline before a change
cargo bench -p forskapd -- --baseline main        # compare against it after
cargo run -p forskapd -- --dry-run                # demo daemon: first stdout line is its FORSKAPD_SOCKET
```

Daemon logging: `FORSKAPD_LOG=debug` (env-filter syntax, default `forskapd=info`).

`forskapd` parses its arguments (clap, `args.rs`) before any side effect; without arguments it runs as the systemd units and the Homebrew service start it. An installed `forskapd` of 0.12.0 or older ignores its arguments and starts a second daemon on the real directories: never run one with arguments.

To verify daemon/CLI changes end-to-end at the real varlink surface, use the `verify` skill (`.claude/skills/verify/SKILL.md`). A `forskapd --dry-run` instance (demo data, no keychain, no GitLab, nothing real touched; writes allowed) is enough for client and CLI changes; an isolated real instance via `XDG_*` overrides is needed for anything about GitLab's actual behaviour — it reads real keychain credentials and talks to the real GitLab, so avoid driving write commands there.

## Workspace layout

- `forskap-api/` — the varlink interface crate. **Single source of truth is `forskap-api/varlink/org.thehoster.forskapd.varlink`**; Rust types/traits are generated from it at build time (`build.rs` + `varlink_generator`). Versioned independently from the workspace and dual-licensed MIT/Apache-2.0 (the rest is GPL-3.0-only).
- `forskapd/` — the daemon. Human-facing interface docs in `forskapd/docs/varlink_interface.md` — keep in sync with the `.varlink` file.
- `forskap-cli/` — binary `forskap`. `src/cmd/` mirrors the command tree (one module per group, one per subcommand inside it); `cli.rs` is `include!`d by `build.rs` for the static carapace spec, so it stays clap-only; bash/zsh/fish complete dynamically (clap_complete `unstable-dynamic`, pinned exactly): `main` answers a `COMPLETE=<shell>` request before anything else, and `complete.rs` attaches the completers for issue/MR numbers and `--project` by argument id, served from the daemon's cache within a short timeout and silent on every failure; an iid that is ambiguous across projects opens a picker (`pick.rs`) on a terminal and stays an error elsewhere; shell-hook snippets under `src/hooks/`; `packaging/` holds the GNOME Shell / KRunner / D-Bus registration files that both `forskap integration search-provider install` (via `include_str!`) and the nfpm package ship.
- `clients/go/` — **generated** Go binding. After changing the `.varlink` interface, run `go generate ./...` in `clients/go` and commit the result; CI (`go-binding.yml`) fails if the committed binding is stale. Never hand-edit `orgthehosterforskapd.go`. Each interface version on `main` is tagged `clients/go/v<forskap-api version>` — the tag `go get` resolves; a pushed one is never moved.
- `forskap/` + `catalog.toml` — noctalia-shell launcher provider (`/gl`, Luau + `plugin.toml`). Shells out to `forskap search --output json` / `forskap issue|mr open`; no daemon access of its own. The repo root is a noctalia plugin *source* (`plugins source add … git <repo>`): the plugin dir must equal the id suffix and `catalog.toml` mirrors `plugin.toml` (id, version, plugin_api) — bump both together.
- `Formula/forskap.rb` — Homebrew formula; the repo root is also a tap (`brew tap bjarneseger/forskap <repo url>`). Generated, not hand-edited: `.github/scripts/render-formula.sh` renders it from a version, a base URL and a GoReleaser checksums file — per-platform `url`/`sha256` of the prebuilt release archives (macOS arm64, Linux amd64/arm64; a custom requirement turns Intel Macs away and points to `--HEAD`), `head` building from source, the launchd/`brew services` definition. Every release archive has one layout (binaries, `LICENSE`, `README.md`, `completions/`): `.github/scripts/package-release.sh` defines it, the GoReleaser `archives` entry mirrors it. Release flow: `release.yml`'s `macos` job builds and packs the macOS archive natively (Apple's SDK; also on main pushes, so a macOS-only break shows before a tag) and hands it to the GoReleaser job as a workflow artifact (`dist-darwin/`, gitignored), whose `release.extra_files`/`checksum.extra_files` publish and checksum it; on a stable tag `bump-formula` re-renders the formula from the published checksums (`bump-formula.sh`, `gh release download`), commits it to `main` and calls `brew.yml` in `stable` mode, which installs and tests the formula on macOS (arm64) and Linux and runs the daemon under launchd. Until the first release with these archives the committed formula is still the old source-building one. On pushes and pull requests touching the formula, those scripts, `.goreleaser.yaml`, the manifests or the lockfile, `brew.yml` (`checkout` mode) builds the checkout with cargo, packs it, renders the formula for that one archive and installs it — the only macOS build outside a release, so a dependency or feature change that breaks macOS shows up there.

So an interface change typically touches: the `.varlink` file → daemon handler impls → `forskap` command → `docs/varlink_interface.md` → regenerated Go binding. Use the `interface-change` skill for the full checklist. Related skills: `test-patterns` (mock/test conventions before writing daemon tests), `config-key` (adding daemon config keys).

## Daemon architecture (forskapd)

The daemon is built around a shared session slot and the principle that it **never refuses to start or serve**:

- **Session state**: `ConnState` (`Connected(Session)` | `Dormant(DormancyReason)`) lives in `SessionSlot = Arc<RwLock<ConnState>>` (`handlers/mod.rs`). Dormant still serves cached reads; auth-requiring calls reply `NotAuthenticated` carrying the specific dormancy reason for the CLI to report.
- **Credentials** come only from the OS keychain (`secrets.rs`; oo7/Secret Service on Linux, Keychain on macOS), set via `forskap auth login` — never from config files. Everything reaches it through a `Keychain` value (`Handlers.keychain`, the sync worker's `KeychainProbe`, boot): `Keychain::Os` is the only path to the OS, `Keychain::Disabled` turns every call down itself and counts it. The Linux backend keeps one Secret Service client for the daemon's life: gnome-keyring 50 can abort when a new D-Bus client's first call is OpenSession (upstream gnome-keyring#190), and each `oo7::Keyring::new` is such a client.
- **GitLab access** is confined to `gitlab.rs`, the only module that knows the `gitlab` crate. It sits behind the `GitlabApi` trait: reads are one generic paginated `list(&Listing)` plus the GraphQL `list_timelogs` and the raw `project_avatar` download, writes are one method each (`create_issue` is the one that returns GitLab's answer), as are the two token calls (`token_info`, `rotate_token`). Every answer is asked for gzip-compressed: `forskapd` depends on reqwest only to switch its `gzip` feature on for the client the `gitlab` crate builds, which a test against a local HTTP server pins. Tests use the shared listing-routed fake in `testing.rs`.
- **Sync** (`sync/`): the only GitLab reader and the only writer of the store. `model.rs` holds serde mirrors of the GitLab resources (issues, MRs, epics, projects, groups, boards, events, timelogs), deserialized straight from responses. `store.rs` keeps one fjall keyspace per resource keyed big-endian (a project's issues or a time window is one range scan), plus views (ordered key lists like "assigned to me"), per-job state and the account identity; a `Commit` lands rows, scope reconciliation and job state in one atomic batch. `engine.rs` runs up to `sync.max_in_flight` fetches at once as spawned tasks and stays the single committer, landing each result as it arrives; one job per `Lane` (`jobs.rs`) at a time — a project, a group's epics, the timelogs, each cross-project listing — and a free slot goes to demanded jobs first, else due jobs by priority, with per-job jittered due times (`schedule.rs`, pure) and a jittered gap between launches. An assigned list and a project's corpus run in different lanes though both store the project's assigned items: when the one that started earlier lands last, it leaves the rows the other stored in a newer version alone (`drop_outdated`). A 429 pauses the launches, a 5xx/rejection backs off only its job (see unavailable jobs below), a network error backs off its job and demotes the session, a 401 parks the session as `TokenRejected` until `forskap auth login` (which clears every job's backoff) unless the keychain holds a newer token; fetches still in flight then finish and land, and their own 429, network error or 401 counts as the same incident (no second pause step, demotion or backoff). A fetch whose job left the plan, or whose account was replaced, is aborted. `planner.rs` derives the per-project jobs from the tracked set: projects with assigned issues/MRs, contribution events (`GET /events`) or timelogs inside `search.tracked_retention_hours` — so it works for users who never log time. Events sync as deltas on the partial cadence and are re-walked whole every `search.full_interval_secs` (GitLab hides rows invisible at walk time and lands imports late); only age removes a stored event. Only tracked *member* projects get a corpus (an assigned MR in gitlab-org/gitlab must not pull its history), capped at `search.max_items_per_project` most recently updated items each. A project's own settings leave jobs out: no `ProjectIssues`/`ProjectBoards` where its member row says issues are switched off (`issues_access_level` `disabled`, or the legacy `issues_enabled` false; boards belong to the issues), no `ProjectMergeRequests` where merge requests or the repository are; a level the row doesn't carry plans as usual (`Project::issues_disabled`/`merge_requests_disabled`, `Plan::switched_off`). The member-projects sync brings a changed setting, and the replan drops or adds the job (pruning its state and rows) like any other plan change. Two more issue lists serve `ListIssues` (`Job::RecentAuthoredIssues`, `Job::RecentAssignedIssues`; views `recent/authored/issues`, `recent/assigned/issues`): the issues the user authored or was assigned, in any state, updated inside `search.tracked_retention_hours`, refetched whole on the slow cadence and after an issue write, in the assigned issues' lane. They are deliberately not the assigned list with a filter (that one is bounded by state, not by time, runs on the quick cadence and feeds the planner) and add no tracked evidence. Every issue view is in `ISSUE_VIEWS`: a row one of them names survives a project's cap, the garbage collection and another view dropping it. Epics (`Job::GroupEpics`, REST `GET /groups/:id/epics`, keyed `(group_id, iid)`) are synced for the member groups above a corpus project and are search/open only — not an `Issuable`; they need GitLab Premium, so a rejected epics fetch makes its job unavailable at once (below). **Unavailable jobs**: `Error::Rejected` keeps the HTTP status of a refusal (`gitlab.rs` `throttled_or_rejected`; `Error::Gitlab` is a failure without one); a per-project/per-group listing (`Job::unavailable_after`: issues, MRs, boards, avatar after 3, epics after 1; never an account-wide one, where a refusal means a broken session) that GitLab refuses (`Job::refused_by`: 403/404; for epics any rejection) that many times in a row is unavailable: it rests `UNAVAILABLE_REST_SECS` (a day) at a time, logs its refusals at debug (the transition once at info), and `GetSyncJobs` reports it `waiting` with `unavailable: true`. The count is `JobState::rejections` (persisted, so a restart stays quiet); network errors, 429, 5xx and 401 leave it, another rejection status (400, 422…) or a fetch GitLab served (even if storing it failed) resets it, as do a success, `forskap auth login` (`unpark`) and a `ClearCache` that resets the job's state. A changed fingerprint doesn't: it never cuts a backoff short. Job states persist: a restart inside an interval costs GitLab nothing. There is deliberately **no TTL** and no read-through.
- **Project avatars** (`sync/avatars.rs`): launchers want a local file and a private project's avatar needs the token, so `Job::ProjectAvatar` (lowest priority, one per member project with an `avatar_url`) downloads `GET /projects/:id/avatar` into `$XDG_CACHE_HOME/forskapd/avatars/`. The job's fingerprint covers the hash of the URL (`Plan::fingerprint`) and only decides when to download: GitLab appends `?v=<updated_at>` to the URL, so any update of the project fetches the image again, and the URL is the only sign of a new image uploaded under the same name. The file is named by the XXH3 of its bytes after the project id (`avatars::file_name`), so its path changes only when the image does and a launcher caching by path keeps its cache: the same image downloaded again leaves its file untouched; a new one is written before its row lands and the old file removed after. Files named by the fingerprint before this keep their name until their project's next download. An `Avatar` row names the file (empty for a 404, an oversized or unknown image), so reads never touch the filesystem. The worker sweeps files no row names after a prune, clear or account change, and at boot drops rows whose file is gone.
- **Reads** are pure store readers (`handlers/varlink.rs`, projections in `handlers/wire.rs`), corrected at read time for writes the sync hasn't picked up yet: a queued or just-applied close/unassign hides the item from the assigned views, and `ListIssues` reads it as closed or no longer assigned. `ClearCache` sends a clear to the worker (cancelling every fetch into the cleared slice) and waits for the jobs refilling what it cleared.
- **Writes** (`PostTime`, `Close`, …) share one cascade (`write.rs` `Write::apply`): try GitLab once, else queue in the persistent `RetryQueue` (`queue.rs`): fjall-backed; one coordinator task owns the stores and launches up to `queue.max_in_flight` attempts at once as spawned futures (writes to one issuable run one at a time, in enqueue order), backs each off exponentially, pauses all launches on a 429, and dead-letters after the retry window (surfaced via `forskap queue`). 429 always retries, 5xx only for idempotent ops (a PostTime may already have landed). A write never demotes the session; once it lands, the jobs displaying it rerun. `CreateIssue` is the one write outside the cascade — not a `WriteOp`, never queued or replayed (no `iid` to address it by, no idempotency key: a replay after a lost answer would file the issue twice), so it fails with `NotAuthenticated`/`GitlabError` while GitLab is away. The created row reaches the store through the sync worker (`SyncHandle::land_issue`): upserted and prepended to the issue views it belongs to (by the answer's assignees), which also voids the issue-list fetches in flight (`Lane::Issues`) — they started before the issue existed and would drop it again.
- **Reconnect** (`reconnect.rs`): a background supervisor retries the connection whenever the session is `Dormant(Unreachable)` — at boot or after the sync worker demotes it mid-run (`commit_unreachable`, guarded on client identity so a stale in-flight failure can't clobber a fresh `forskap auth login` session). The sync worker is the demotion authority; a 429/5xx at connect counts as unreachable, not as a rejected token.
- **Token rotation** (`rotate.rs`): a background supervisor reads the session token's scopes and lifetime (`GET /personal_access_tokens/self`) and rotates it once less than `min(auth.rotate_before_days, lifetime / 3)` is left (moved up to a day earlier by a per-daemon random share, so machines sharing a keychain don't rotate together) — by default only tokens carrying `self_rotate` (`auth.rotate`), never one without an expiry. GitLab revokes the old token with its answer, so the new one is written to the keychain first and the session swapped after (if the keychain keeps failing: swapped anyway, write retried in the background). The swap replaces only the rotated session or what a 401 of its revoked token left of it; a login or logout in between wins. A failed rotation never demotes the session. On a 401 the sync worker asks the keychain before parking the session: if it holds another token (rotated by a machine sharing the keychain), the session goes `Dormant(Unreachable)` and the reconnect supervisor connects with that one.
- **Rename migration** (`migrate.rs`, `secrets.rs`; `migrate.rs` in the CLI): the pre-rename `gitlab-trackrd` / `tt` directories, keychain entry and env vars are moved or still read, and the package ships a `tt` symlink for installed shell hooks.
- **Config**: layered TOML via confique (user `$XDG_CONFIG_HOME/forskapd/config.toml` → package default → baked-in), hot-reloaded by `reload.rs` watching the file; a reload re-plans the sync worker and re-evaluates the token rotation.
- **Startup and dry run** (`main.rs`, `daemon.rs`, `demo.rs`): `main` parses the arguments, builds an `Environment` (session, keychain, config and whether its file is watched, db and avatar dirs, socket) and runs the same `Daemon` on it. `Environment::real` is the user's daemon; `Environment::dry_run` (`--dry-run`) is the seam for the demo mode — no `if dry_run` elsewhere: a `Connected` session on `DemoGitlab` (an in-memory `GitlabApi` over a fixture on `dry-run.invalid`, applying writes to it; not the tests' fake), `Keychain::Disabled`, the baked-in config (`demo::config()`, no file read or watched), db/avatars/socket in a `Scratch` temp dir that `main` removes after the runtime. The reconnect and rotation supervisors run only with `Keychain::Os`, the config watch only for a file; `Login`/`Logout` check `Keychain::require` first, so a dry run refuses them before GitLab or the session is touched. A dry run prints its `unix:` address on stdout once `daemon::synced` (logs go to stderr).

## forskap-cli conventions

`forskap` is deliberately thin: argument parsing, local state, interactive UI — all GitLab access goes through the daemon socket. GitLab issues have a global `id` and a per-project `iid`; users know the `iid`, so `forskap issue` / `forskap mr` take the `iid` positionally and resolve the project lazily (`cmd/project.rs`). Text views take their colours from the named helpers in `style.rs` (state, heading, reference, error), which also settles `--color`; pad with the helper's value (`{:<8}`), never around a styled string.

## Error handling

Prefer thiserror `#[from]` derivation over hand-written `From` impls. The daemon distinguishes transient (network), throttled (429/5xx) and permanent errors (`error.rs`); that split drives queue-retry vs dead-letter, session demotion vs per-job backoff, and connect-time dormancy reasons. A permanent error with an HTTP status is `Rejected { status, .. }` (401 is `Unauthorized`), one without is `Gitlab`: writes and the connect check treat both alike, only the sync tells a refused listing (403/404) by the status.
